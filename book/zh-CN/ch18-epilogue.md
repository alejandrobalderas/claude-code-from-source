# 第 18 章：我们学到了什么

## 五项架构取舍

智能体系统早已有之，也有许多不同的实现。Claude Code 做出了五项架构取舍，使它在众多智能体框架中独具特色。读过近两千个文件，走过十七章之后，值得回头审视这些决定。

### 取舍一：用生成器实现循环

多数智能体框架提供一条流水线：开发者定义工具、注册处理函数，再由框架编排整个过程。开发者编写回调，框架决定何时调用它们。

Claude Code 让开发者掌控循环。`query()` 函数是一个 AsyncGenerator（异步生成器）。模型以流式处理（Streaming）的方式输出响应，生成器产出工具调用，调用方执行工具并追加结果，生成器再进入下一轮。只有一个函数、一条数据流，每次交互都经过同一个地方。生成器返回类型中的 10 种终止状态和 7 种继续状态涵盖所有可能的结果。循环就是系统的核心。

这项取舍的出发点是，即使生成器增长到 1,700 行，单个函数也比散布在各处的回调关系更便于理解。从源码看，这一判断得到了验证。要理解会话为何结束，只需检查一个函数。要添加新的终止状态，只需为一个可辨识联合类型增加一个变体，类型系统负责确保各个变体都得到处理。回调架构会把相关逻辑分散到几十个文件，回调之间的关系也很难直接从控制流看出。

### 取舍二：用文件保存记忆

[第 11 章](ch11-memory.md)详细讨论了这项取舍，它的架构意义还超出了记忆系统本身。选择普通 Markdown 文件，体现了系统对透明度的重视。SQLite、向量数据库或云服务能支持更丰富的查询、更快的查找和事务保证，而文件提供的是可检查性，由此建立信任。

用户在 Vim 中打开 `~/.claude/projects/myapp/memory/MEMORY.md`，就能确切知道智能体（Agent）记住了哪些关于自己的信息。这与只能问智能体“你记得什么”并期望它如实、完整地回答，有着根本区别。文件设计让外部可以直接观察智能体的知识状态。这比查询性能更重要。存储虽简单，基于 LLM 的记忆检索（Recall）弥补了这一点。通过 Sonnet 发起旁路查询，从清单中选出五条相关记忆，比用嵌入向量相似度更精确，也无需额外的基础设施。

### 取舍三：让工具自行描述

智能体框架通常会提供工具注册表。开发者在中央配置中描述工具，再由框架将它们呈现给模型。Claude Code 的每个 `Tool` 对象都带有自己的名称、描述、输入模式、对提示词的补充、并发安全标志和执行逻辑。工具系统给每个工具提供了自行描述的途径。

这项设计便于扩展。MCP 工具（[第 15 章](ch15-mcp.md)）实现同一个接口后，就能作为一等工具使用。在模型看来，MCP 服务器提供的工具和内置工具采用相同的形式。包装过程生成标准的 `Tool` 对象，之后由现有的工具流水线处理权限检查、并发执行、结果预算（Result Budget）和 Hook（钩子）拦截。

### 取舍四：用分叉智能体共享缓存

[第 9 章](ch09-fork-agents.md)介绍了分叉机制。子智能体（Sub-Agent）启动时，上下文窗口中已经包含父智能体的完整对话，并共享父智能体的提示词缓存（Prompt Cache）。这项取舍认为，共享缓存带来的收益值得承担管理分叉生命周期的复杂性。

另一种方法是根据对话摘要启动一个全新的智能体。做法更简单，但每个新智能体都得从头处理上下文，按全价支付费用。分叉智能体（Fork Agent）可以复用父智能体已缓存的前缀，输入 token 享受 90% 的折扣，因此连记忆提取、代码审查、验证等小任务也可以交给单独的智能体。后台记忆提取智能体（[第 11 章](ch11-memory.md)）会在查询循环（Query Loop）的每一轮之后运行，正因为共享了父智能体的缓存，额外成本才很低。失去分叉带来的缓存共享，这个智能体的运行成本将高得难以接受。

### 取舍五：通过 Hook 扩展行为

多数扩展系统采用插件，由插件注册能力，并在宿主进程内运行代码。Claude Code 采用 Hook，在生命周期节点上启动外部进程，通过退出码和 stdin、stdout 上的 JSON 通信。

这一取舍认为隔离进程值得付出额外开销。插件崩溃可能带崩宿主，Hook 崩溃只影响自己的进程。插件可能在宿主堆中留下内存泄漏，Hook 进程退出时自身内存便被回收。插件需要维护带版本的 API 接口，Hook 只需要 stdin、stdout 和退出码，这套协议自 1971 年便已稳定。

这确实有运行开销。每次调用 Hook 都创建进程，会比进程内回调多花几毫秒。内部回调的快速路径将开销减少 70%（[第 12 章](ch12-extensibility.md)），表明系统也在认真处理这笔成本。对用户脚本、团队静态检查工具和企业策略服务器等外部 Hook，进程隔离让扩展更安全。企业采用 Hook 落实策略时，可以避免格式错误的 Hook 脚本使开发者的会话崩溃。

## 设计模式的适用范围

Claude Code 的一些做法可以推广，另一些来自它的规模、资源或特定约束，其他智能体开发者未必面临同样的情况。

### 适用于各类智能体的模式

**显式的生成器循环。** 需要流式输出响应、处理工具调用和管理多种终止状态的智能体，都可以用生成器把循环写在控制流中。返回可辨识联合类型，精确记录循环停止的原因，就能消除一类以“智能体为什么停了”为起点的调试工作。

**让 LLM 检索文件中的记忆。** 具体实现属于 Claude Code，但简单存储配合智能检索，适用于任何需要跨会话保留知识的智能体。将记忆划分为用户、反馈、项目和参考四类，以及询问“能否从当前项目状态重新推导出这条信息”，都是可以复用的设计方法。

**用于远程执行的非对称读写通道。** 当读取是高频数据流、写入是低频 RPC 时，应拆分读写通道。这个原则与所用的具体传输协议无关。

**在搜索中用位图预过滤。** 智能体需要搜索大量文件索引时，可以先用 26 位字母位图筛选。每项只占四字节，每个候选项只需一次整数比较，开销很低。

**在架构中考虑提示词缓存的稳定性。** 智能体使用带提示词缓存的 API 时，应将稳定内容放在开头、易变内容放在末尾。这项决定会直接影响成本结构。

### 适用于 Claude Code 规模的模式

**基于 Ink 分叉的终端渲染器。** Claude Code 分叉了 Ink，用紧凑的类型化数组、基于池的驻留和单元格级差异比较重新实现了渲染流水线，以便在终端中以 60 帧每秒呈现流式输出。多数智能体使用网页界面或简单的日志输出。这笔工程投入只适用于以终端为主要界面、且需要高频流式输出的系统。

**50 多个启动性能分析检查点。** 当用户数量达到几十万，0.5% 的采样就能得到具有统计意义的数据，这些检查点才有价值。较小的智能体系统用更简单的计时机制即可。

**八种 MCP 传输类型。** Claude Code 支持 stdio、SSE、HTTP、WebSocket、SDK、两种 IDE 变体和 Claude.ai 代理，以适配各种部署拓扑。多数智能体只需要 stdio 和 HTTP。

**Hook 快照安全模型。** 启动时冻结配置，之后避免隐式重读，可以防止恶意仓库代码在用户通过信任确认后修改 Hook。智能体要在任意仓库中运行，遇到不可信的 `.claude/` 配置时，这项防护很重要。只在受信环境中运行的智能体可以简化 Hook 管理。

## 复杂性的代价

近两千个文件带来了什么，又要为此付出什么？

文件数量很容易让人误判复杂程度。很多文件属于测试基础设施、类型定义、配置模式以及分叉后的 Ink 渲染器。行为上的复杂性集中在少数密度很高的文件中，包括 `query.ts`（1,700 行，实现智能体循环）、`hooks.ts`（4,900 行，实现生命周期拦截系统）、`REPL.tsx`（5,000 行，负责交互式编排），以及记忆系统中构造提示词的函数。

复杂性来自三方面，各有不同特点：

**协议多样性。** 同时支持五种终端键盘协议、八种 MCP 传输类型、四种远程执行拓扑和七个配置作用域，本身就很复杂。每支持一种协议，代码库的规模会线性增长，累积起来仍相当可观。按 Brooks 的说法，这属于偶然复杂性，来自终端碎片化、MCP 传输方式演进和远程部署拓扑等环境差异。

**性能优化。** 基于池的渲染、位图搜索预筛选、保持型缓存锁存标志和工具推测执行（Speculative Execution），都以增加复杂性换取可衡量的性能提升。这些优化有测量数据作为依据。每项优化前都通过性能分析数据定位了瓶颈。风险在于优化逐渐累积、相互作用，使热路径越来越难修改。

**行为调校。** 记忆系统中的提示词指令、过时警告、验证协议，以及避免忽略记忆的反模式指令，都属于提示词复杂性，带来不同于代码的维护负担。模型版本变化时，经过评测精细调校的提示词可能需要重新调整。代码库各处引用的用例编号和评测分数来自评测基础设施，通过持续投入来防止行为退化。

维护这套系统需要投入大量精力。工程师刚开始读代码时，除了理解代码路径，还得了解哪些评测结果促成了特定的提示词措辞、哪些生产事故促成了特定的安全检查，以及哪些性能数据促成了特定的优化。代码注释很详尽，不少还包含评测用例编号和修改前后的测量结果。但近两千个文件中的大量注释本身也增加了阅读负担。

## 智能体系统的演进方向

Claude Code 的实现体现了四个趋势，反映出这一领域可能的发展方向。

### MCP 成为通用协议

[第 15 章](ch15-mcp.md)把 Claude Code 描述为实现较为完整的 MCP 客户端之一。真正重要的是 MCP 本身。工具发现和调用有了标准化协议，为一个智能体构建的工具就可以被支持同一协议的其他智能体使用。例如，一旦做出 Postgres 的 MCP 服务器，所有使用 MCP 的智能体都能接入。开发者为集成工具投入的工作可以跨系统复用。

对智能体开发者而言，自行定义工具协议很可能不划算。MCP 已经基本够用，还在继续改进，而标准协议的生态优势会随着时间积累。可以构建 MCP 客户端、参与规范制定，让协议在社区反馈中演进。

### 多智能体协调

Claude Code 的子智能体系统（[第 8 章](ch08-sub-agents.md)）、任务协调（[第 10 章](ch10-coordination.md)）和分叉机制（[第 9 章](ch09-fork-agents.md)）是多智能体模式的早期实现。它们解决了缓存共享、并行探索和结构化验证等具体问题，也暴露了一个基本难题：协调开销。

智能体之间的每条消息都会消耗 token。每次分叉都能共享缓存，也会新增一条最终需要父智能体整合的对话分支。Task 系统的状态机（排队、运行、完成、失败、取消）增加了协调上的复杂性，本身并不增加能力。随着智能体能力增强，关注点将从“如何协调多个智能体”转向“如何让一个智能体足够强大，能够独自完成任务”。

现有证据表明，两种方式会并存。简单任务交给单个智能体，复杂任务由多个智能体协调处理。工程上的挑战是把协调开销降到足够低，让真正可以并行的工作达到采用多智能体更划算的临界点。仅凭任务复杂，还不足以判断多智能体是否有利。

### 持久记忆

Claude Code 的记忆系统是持久化智能体记忆的第一版。文件存储、四类记忆、由 LLM 执行的记忆检索、过时判定和面向长期会话的 KAIROS 模式，都是这一问题的第一代方案，今后还会有很大变化。

未来的记忆系统可能加入结构化检索。目前系统取回完整文件，今后可能直接取回具体事实。也可能加入跨项目迁移学习，区分可在各处适用的用户偏好和只适用于特定项目的约定。协作记忆也会发展，[第 11 章](ch11-memory.md)的团队记忆已经迈出第一步，但同步、冲突解决和访问控制功能仍很有限。

有待观察的是，文件方案能否扩展到更大的规模。每个项目有 200 条记忆时，它可以正常工作。达到 2,000 条时，Sonnet 旁路查询使用的清单会过大，整合成本会上升，索引也会超过上限。随着使用量增长，以文件为基础的设计将面临最严格的考验。

### 自主运行

KAIROS 模式、后台记忆提取智能体、自动做梦整合和工具推测执行，都在推动系统走向自主运行。无需用户明确要求，智能体就可以完成有用的工作。它会记住用户忘了让它记住的事，在用户睡觉时整合知识，并在当前响应结束前开始执行下一个工具调用。

未来的智能体将从被动响应走向主动行动。它们会识别用户没有描述的模式，提出用户没有要求的修正，并在无需显式调用 `/remember` 的情况下维护自身的知识。Claude Code 的记忆系统为此提供了原型。后台提取机制为记忆保留兜底，提示词中设计的判断规则决定应该保存哪些信息。

制约自主运行的是信任。用户需要相信，在无人监督时，智能体也会做正确的事。文件记忆、可观察的 Hook 系统、过时警告和权限对话框都在提供建立信任的依据。智能体越走向自主，就越需要让用户看清它的行为。

## 结语

十七章，六项核心抽象。生成器循环居于中心，工具向外延伸，记忆回溯过去，Hook 守住执行边界。渲染引擎将这些活动转化为屏幕上的字符，MCP 则把系统连接到代码库之外。

Claude Code 反复做出的一项设计决定，是把复杂性放到边界处理。渲染系统把复杂性集中到驻留池和差异比较，流水线中只做整数比较。输入系统让分词器和键位绑定解析器承担复杂性，处理函数只接收类型明确的动作。记忆系统把复杂性留给写入协议和记忆筛选过程，向对话提供可直接使用的上下文。智能体循环把复杂性放进终止状态和工具系统，循环体依次执行流式接收、收集、执行、追加，再进入下一轮。

每个边界都把外部差异转化成系统可以处理的结构。原始字节变成 `ParsedKey`，Markdown 文件变成检索出的记忆，MCP JSON-RPC 变成 `Tool` 对象，Hook 退出码变成权限决策。边界的一侧是五种键盘协议、脆弱的 OAuth 服务器、过时的记忆和不可信的仓库 Hook。另一侧则是类型明确、范围有限、每种情况都有对应处理的数据。

构建智能体系统时，可以把这一原则带走。你未必需要基于池的渲染、KAIROS 模式或八种 MCP 传输。先定义边界，在边界上处理复杂性，让各边界之间的代码保持清晰。工程上最难处理的工作集中在边缘，内部就更容易理解和维护。

源码是开放的，螃蟹的钳子里夹着地图。去读读源码吧。
