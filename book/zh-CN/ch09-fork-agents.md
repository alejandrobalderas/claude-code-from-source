# 第 9 章：分叉智能体与提示词缓存

## 95% 的重合意味着什么

父智能体（Agent）并行启动五个子智能体（Sub-Agent）时，每个子智能体的 API 请求绝大部分都相同。系统提示词相同，工具定义相同，对话历史相同，触发这些子智能体启动的助手消息也相同。唯一的差别是最后的任务指令，比如“你负责数据库迁移”“你编写测试”“你更新文档”。

在已有对话的典型分叉中，共享前缀可能有 80,000 个 token，每个子智能体的专属指令可能有 200 个 token，重合度达到 99.75%。Anthropic 的提示词缓存（Prompt Cache）让命中的输入 token 享受 90% 的折扣。如果第 2 至第 5 个子智能体的这 80,000 个 token 都能命中缓存，这四次请求的输入费用就能降低约 90%。对父智能体来说，同样一次并行分派，费用可以从 4 美元降至 0.50 美元。

提示词缓存要求逐字节精确匹配。从系统提示词的首字节，到各子智能体内容开始分歧之前的最后一个字节，必须完全一致。多一个空格、换一下工具定义的顺序，或用旧的功能开关值改变系统提示词中的某个片段，都足以造成缓存未命中。整个前缀将重新处理，并按原价计费。

分叉智能体（Fork Agent）是 Claude Code 应对这一约束的方式。它通过编排（Orchestration）机制启动继承上下文的子智能体，并借此提高提示词缓存的利用率。分叉系统的每项设计决策，都围绕着如何确保并行子智能体的前缀逐字节一致展开。

---

## 分叉子智能体继承什么

分叉智能体从父智能体继承四项内容，方式是直接传递引用或逐字节复制。

**1. 系统提示词。** 系统从 `toolUseContext.renderedSystemPrompt` 取出父智能体已经渲染好的系统提示词，通过 `override.systemPrompt` 传递。这正是父智能体最近一次 API 调用发送的完整字符串。

**2. 工具定义。** 分叉智能体的定义声明了 `tools: ['*']`。当 `useExactTools` 标志设为 true 时，子智能体会直接接收父智能体已经组装好的工具数组。工具定义的集合、顺序和序列化结果全都保持一致。

**3. 对话历史。** 父智能体与 API 交换过的每条消息，包括用户消息、助手消息、工具调用和工具结果，都会通过 `forkContextMessages` 克隆到子智能体的上下文中。

**4. 思考配置与模型。** 分叉定义指定 `model: 'inherit'`，解析后得到父智能体使用的同一个模型。模型相同，也就意味着分词器、上下文窗口和缓存命名空间相同。

分叉智能体自身的定义非常精简，几乎无需执行任何操作：

分叉智能体的定义刻意保持精简，所需内容全部继承自父智能体。它指定所有工具（`'*'`），继承父智能体的模型，并对权限采用向上传递模式，使权限请求显示在父智能体的终端中。系统提示词函数只是一个空操作，实际不会调用。真正的提示词会通过覆盖参数传入，已经渲染完成，字节内容也已固定。

## 如何构造逐字节一致的前缀

Claude API 请求采用固定的结构，依次包含系统提示词、工具和消息。要命中提示词缓存，从请求开头到某个前缀边界之间的每个字节，都必须在不同请求之间完全一致。

分叉智能体通过固定三层内容做到这一点：

**第 1 层：直接传递已渲染的系统提示词。**

父智能体为最近一次 API 调用渲染系统提示词时，渲染结果已存入 `toolUseContext.renderedSystemPrompt`。此时字符串已经完成所有动态插值，包含 GrowthBook 功能开关、环境信息、MCP 服务器描述、Skill（技能）内容和 CLAUDE.md 文件。分叉子智能体直接接收这个字符串。

为什么不能再调用一次 `getSystemPrompt()`？因为生成系统提示词的过程有外部状态。SDK 拉取远程配置后，GrowthBook 的开关会从冷状态转为就绪状态。父智能体第一轮交互时返回 `false` 的开关，到分叉子智能体启动时可能已返回 `true`。如果系统提示词中有受该开关控制的条件内容块，重新渲染后哪怕只差一个字符，也会导致缓存未命中。五个子智能体都会重新处理 80,000 个 token，并按原价计费。

直接传递已渲染的字节，可以杜绝这一类差异。

**第 2 层：原样传递工具定义。**

普通子智能体会调用 `resolveAgentTools()`。这个函数根据智能体定义中的 `tools` 和 `disallowedTools` 数组筛选工具池，应用权限模式的差异，还可能重新排列工具。所得工具数组在序列化后会与父智能体的不同，差异可能来自工具子集、顺序或权限标注。

分叉智能体直接跳过这一步：

```typescript
const resolvedTools = useExactTools
  ? availableTools  // parent's exact array
  : resolveAgentTools(agentDefinition, availableTools, isAsync).resolvedTools
```

`useExactTools` 标志仅在分叉路径上设为 true。子智能体原样接收父智能体的工具池，工具、顺序和序列化结果都相同。其中也保留了 Agent 工具。虽然子智能体不得使用该工具，但移除它会改变工具数组，导致缓存未命中。

**第 3 层：构造消息数组。**

这一步由 `buildForkedMessages()` 处理。它构造最后两条消息，衔接共享历史与各子智能体的专属指令：

`buildForkedMessages()` 函数构造最后两条消息，衔接共享历史和各子智能体的专属指令。算法如下：

1. 克隆父智能体的助手消息，保留所有 `tool_use` 块及其原始 ID。
2. 为每个 `tool_use` 块创建一个 `tool_result`，填入所有子智能体共用的固定占位字符串。
3. 构造一条用户消息，先放入全部占位结果，最后追加用固定模板标签包裹的专属指令。
4. 返回 `[clonedAssistantMessage, userMessageWithPlaceholdersAndDirective]`。

```typescript
// Pseudocode — illustrates the message construction
function buildChildMessages(directive, parentAssistant) {
  const cloned = cloneMessage(parentAssistant)
  const placeholders = parentAssistant.toolUseBlocks.map(b =>
    toolResult(b.id, CONSTANT_PLACEHOLDER)  // Byte-identical across children
  )
  const userMsg = createUserMessage([...placeholders, wrapDirective(directive)])
  return [cloned, userMsg]
}
```

每个子智能体得到的消息数组形如：

```
[...shared_history, assistant(all_tool_uses), user(placeholder_results..., directive)]
```

专属指令前的所有元素在不同子智能体之间都完全一致。`FORK_PLACEHOLDER_RESULT` 是固定字符串 `'Fork started -- processing in background'`，确保连工具结果块也逐字节一致。`tool_use_id` 的值同样一致，因为它们引用的是同一条助手消息。只有包含专属指令的最后一个文本块会变化。

缓存边界位于最后一个文本块之前。在此之前的内容可能有数万个 token，涵盖系统提示词、工具定义、对话历史和占位结果。第一个子智能体之后的每个子智能体都能命中这部分缓存，获得 90% 的折扣。

## 分叉指令的固定模板标签

各子智能体的专属指令都用固定模板的 XML 标签包裹。标签既承载对子智能体的行为要求，也作为检测递归分叉的标记。

模板约有 10 条规则，主要包括：

- **覆盖父智能体的分叉指令。** 父智能体的系统提示词要求“默认分叉”。模板明确告诉子智能体：“那条指令适用于父智能体。你就是被分叉出来的子智能体。不得再启动子智能体。”
- **静默执行，只汇报一次。** 工具调用之间不输出对话文本。直接使用工具，完成后给出结构化摘要。
- **守住任务范围。** 子智能体不得超出专属指令划定的范围。
- **采用结构化输出。** 响应必须遵循 Scope/Result/Key files/Files changed/Issues 模板，以便多个子智能体同时回报时，父智能体能够解析结果。

第一条规则涉及一个继承问题。为了命中缓存，分叉子智能体逐字继承父智能体的系统提示词，其中可能包括“有可并行的工作时，默认分叉”之类的指令。如果子智能体照做，就会尝试分叉出自己的一批子智能体，造成无限递归。因此模板明确覆盖了这条指令：“那条指令适用于父智能体。你就是被分叉出来的子智能体。”

结构化输出格式（Scope/Result/Key files/Files changed/Issues）将子智能体的输出限定为事实汇报。五个子智能体同时回报时，父智能体也能更容易地解析并汇总结果。

## 防止递归分叉

分叉子智能体的工具池必须保留 Agent 工具。移除该工具会改变序列化后的工具数组，导致提示词缓存未命中。如果子智能体确实调用 Agent 工具但未指定 `subagent_type`，分叉路径将再次触发，产生下一代分叉智能体。下一代会继承范围更大的上下文，即父子两代的对话，并持续分叉下去。

系统通过两项检查阻止递归分叉：

**主要检查：检查 querySource。** 启动分叉子智能体时，系统将其 `context.options.querySource` 设置为 `'agent:builtin:fork'`。`call()` 方法会检查此值，再决定是否允许进入分叉路径：

```typescript
// In AgentTool.call():
if (effectiveType === undefined) {
  // Fork path -- but are we already in a fork?
  if (querySource === 'agent:builtin:fork') {
    // Reject: already a fork child
  }
}
```

这是快速路径，只需比较选项对象中的一个字符串。

**后备检查：扫描消息。** 系统先检查启动时设置的 `querySource` 标记，这一步只需比较一个字符串。后备检查则扫描消息历史，查找固定模板的 XML 标签。自动压缩（Auto-Compact）会保留 `querySource`，但少数情况下如果未正确传递此值，后备扫描仍能捕获递归。与意外递归分叉导致失控的 API 费用相比，多做一次消息扫描的开销很小。

为什么需要后备检查？当上下文过长时，Claude Code 的自动压缩功能会改写消息数组。自动压缩可以改写消息内容，但会保留选项中的 `querySource`。理论上，仅凭 `querySource` 就够了。实际运行中，扫描消息可以捕捉 `querySource` 未正确传递的边缘情况。相比意外递归分叉带来的失控 API 支出，这项后备检查的开销微不足道。

## 从同步转为异步

分叉子智能体开始时在前台运行，消息以流式方式发往父智能体的终端，父智能体会阻塞等待任务完成。如果子智能体耗时过长，Claude Code 支持在执行中途转入后台。用户可以手动触发，也可以由超时机制自动触发，已经完成的工作能够保留。

切换过程如下：

1. 通过 `registerAgentForeground()` 注册前台智能体时，系统会创建一个用于传递后台切换信号的 Promise。

2. 父智能体的同步循环同时等待智能体消息流和后台切换信号，由先到者决定下一步：

```
while (true) {
  const result = await Promise.race([
    iterator.next(),         // next message from agent
    backgroundSignal,        // "move to background" trigger
  ])
  if (result === BACKGROUND_SIGNAL) break
  // ... process message
}
```

3. 后台切换信号触发后，系统调用 `iterator.return()` 正常终止前台迭代器。这会触发生成器的 `finally` 块，执行清理工作。

4. 系统以 `isAsync: true` 启动新的 `runAgent()` 实例，并使用相同的智能体 ID 和截至此刻累积的消息历史。智能体从上次停下的地方继续，在后台运行。

5. 原先的同步 `call()` 返回 `{ status: 'async_launched' }`，父智能体继续对话。

消息历史就是智能体的状态，因此已完成的工作能够保留。磁盘上的侧链会话记录（Sidechain Transcript）保存了智能体已生成的每条消息。新的异步实例重放这份记录，从同步实例停止的位置继续。

## 自动转入后台

启用环境变量 `CLAUDE_AUTO_BACKGROUND_TASKS` 或 GrowthBook 功能开关 `tengu_auto_background_agents` 后，前台智能体会在 120 秒后自动转入后台：

通过环境变量或功能开关启用后，前台智能体会在 120 秒后自动转入后台。禁用时，函数返回 0，表示关闭自动转入后台。

这一设计影响用户体验，也影响成本。前台智能体会阻塞父智能体的终端。用户无法输入、发出新指令或启动其他智能体。两分钟足以让智能体同步完成大多数短任务，用户可以据流式输出了解进度。长任务则不会让终端一直无法使用。

分叉实验开启时，所有分叉子智能体从启动起就强制异步运行，因此无需考虑自动转入后台。`run_in_background` 参数完全不出现在参数模式中。每个分叉子智能体都在后台运行，完成后通过 `<task-notification>` 回报，父智能体无需阻塞等待。

## 禁用分叉的情形

分叉是多种编排模式之一，系统在以下三种情形中禁用分叉：

**协调模式。** 协调模式与分叉模式互斥。协调器采用结构化的委派模型：维护计划、通过明确的提示词给执行者分配任务，并跟踪进度。分叉的全量继承会破坏这一机制。分叉出来的协调器会继承父协调器的系统提示词，其中要求“你是协调器，应委派任务”。于是子智能体会试图继续编排，对实际任务无从下手。`isForkSubagentEnabled()` 会先调用 `isCoordinatorMode()`，如果协调模式已启用，便返回 false。

**非交互式会话。** 使用 SDK 和 API 的调用方，例如 `--print` 模式和 Claude Agent SDK，不通过交互式终端运行。分叉依靠 `permissionMode: 'bubble'` 将权限提示传到父智能体的终端。非交互式模式缺少这个终端，因此直接禁用分叉路径。SDK 调用方通过显式指定 `subagent_type` 选择子智能体。

**显式指定 subagent_type。** 模型指定 `subagent_type` 时，例如 `"Explore"`、`"Plan"` 或 `"general-purpose"`，不会触发分叉路径。省略 `subagent_type` 才会触发分叉。指定类型可以选择拥有自己系统提示词和工具集的专用智能体。省略类型，则可以派出继承当前上下文的副本来并行处理任务。

## 成本分析

设想开发者要求 Claude Code 重构一个模块。父智能体分析代码库、制定计划，然后并行派出五个分叉子智能体，分别更新数据库模式、重写服务层、更新路由、修复测试和更新类型。

此时对话的共享上下文已相当长：
- 系统提示词：约 4,000 个 token
- 工具定义（40 多个工具）：约 12,000 个 token
- 对话历史（分析和规划）：约 30,000 个 token
- 包含五个 tool_use 块的助手消息：约 2,000 个 token
- 占位工具结果：约 500 个 token

共享前缀共约 48,500 个 token。每个子智能体的专属指令约 200 个 token。

未使用分叉时，五个独立智能体各有全新的上下文和自己的系统提示词：
- 每个子智能体分别处理自己的系统提示词、工具和任务提示词。
- 系统提示词和工具集各不相同，无法共享缓存。
- 成本相当于 5 次全价输入处理。

使用分叉时，前缀逐字节一致：
- 第 1 个子智能体按原价处理 48,700 个 token，首次请求未命中缓存。
- 第 2 至第 5 个子智能体各按原价的 10% 处理 48,500 个 token，即命中缓存的部分，再按原价处理 200 个 token。
- 第 2 至第 5 个子智能体的实际成本各约相当于按原价处理 4,850 + 200 = 5,050 个 token。

上下文越长、子智能体越多，缓存越能节约成本。对已有 100K 个 token 历史的会话，如果并行启动 8 个分叉子智能体，相对于不共享缓存的输入成本，节省比例可超过 90%。

因此，分叉系统的各项决策都服务于逐字节一致的前缀。从直接传递渲染结果、原样传递工具，到使用占位结果，甚至保留子智能体不得使用的 Agent 工具，每项设计都牺牲了一点简洁性或安全性，换来可衡量的 API 成本下降。

## 设计权衡

分叉系统做出了几项明确的取舍：

**隔离性与缓存效率。** 分叉子智能体继承全部内容，包括与其任务无关的对话历史。重写测试的子智能体用不上父智能体讨论数据库模式设计的那 15 条消息，但这些消息是保持前缀一致所必需的。删去无关历史会腾出上下文窗口空间，也会导致缓存未命中。这一设计假定缓存带来的节省足以抵消上下文开销。

**安全性与缓存效率。** 虽然分叉子智能体不得使用 Agent 工具，该工具仍保留在其工具池里。删除它会更安全，因为子智能体连尝试分叉的机会都没有，但也会改变工具数组的序列化结果。系统用固定模板标签和防止递归分叉的检查作为补偿措施，在运行时阻止再次分叉。

**简单性与缓存效率。** 占位工具结果并非真实结果。无论父智能体的助手消息中各个 tool_use 块对应的调用实际做了什么，子智能体看到的结果一律是 `'Fork started -- processing in background'`。专属指令已说明子智能体应做什么，它无需看到父智能体在分派任务这一轮生成的真实工具结果。因此子智能体历史在技术上并不连贯。选用占位结果看重的是简洁和一致。

这些权衡都反映出同一个优先级。在大规模按 token 为 API 调用付费时，保持前缀逐字节一致的收益，足以推动架构发生较大的变化。

## 实践建议：为提示词缓存效率而设计

分叉智能体的模式也适用于 Claude Code 以外的系统。只要从同一上下文发起多次并行 LLM 调用，就可以在构造请求时利用缓存。可采用以下原则：

**1. 直接传递已渲染的提示词。** 系统提示词包含功能开关、时间戳、用户偏好或 A/B 测试变体等动态内容时，保存渲染结果，并按值传给子智能体。重新计算可能产生差异。

**2. 固定工具数组。** 如果子智能体需要不同的工具集，工具块就无法共享缓存。可以考虑保留完整工具集，并通过运行时检查限制调用，例如分叉模板中的“不得使用 Agent”规则。

**3. 尽量延长共享前缀，缩短专属后缀。** 构造消息数组时，让共享内容全部居前，各子智能体的专属内容追加在末尾。交错排列共享内容与专属内容会切碎缓存边界。

**4. 对可变内容使用固定占位符。** 消息结构要求为此前的工具调用提供响应时，给所有子智能体使用相同的占位字符串，以防真实结果的差异打断共享前缀。

**5. 计算盈亏平衡点。** 共享缓存也有成本。每个子智能体占用更多上下文空间，因为连无关历史也要携带。安全检查移到运行时，架构也更加复杂。算入额外的上下文 token 后，再根据子智能体数量和共享前缀长度计算这种并行方式是否真的省钱。

分叉智能体系统的核心是充分利用提示词缓存。每个多智能体系统的开发者迟早都会面对一个问题：重复前缀能获得 90% 的折扣，为了拿到这笔折扣，你愿意对架构做多大的调整？Claude Code 为此大幅调整了架构。
